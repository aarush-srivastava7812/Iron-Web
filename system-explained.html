01 / System overview

Three parts, with distinct responsibilities.

Voyara coordinates a travel conversation, Iron Web preserves memory, and TinyFish supplies current public web evidence.

01

Voyara · product + agents

The traveler explains needs and revises a trip. Nine local agent roles coordinate research, itinerary planning, budget review and support. Trips and user edits remain editable and persistent.

02

Iron Web · shared memory

FalkorDB stores source vectors alongside graph relationships and claim history. Exact claim recall and semantic discovery serve different questions. SQL separately preserves trips and external evidence versions.

03

TinyFish · web research

Search discovers URLs; Fetch reads public pages. Quoted evidence can enter the destination research ledger. An optional Agent adapter supports asynchronous browser goals for research roles.

Key point Personal preferences and public web observations have separate authority and freshness rules.

02 / Memory foundations · vector

Find relevant memories even when words change.

Vector retrieval represents source text as embeddings and searches for semantically nearby sources.

01

What enters the index

A stored source has text, an identity and metadata. Its embedding makes it discoverable without requiring the next query to repeat the original wording.

02

Why it is useful

A query about peaceful accommodation can discover relevant source text about quiet stays. This is an illustration of semantic matching, not a scored query from our benchmark.

03

What similarity cannot decide

A nearby result is a candidate, not a truth certificate. Scope, validity and source status still matter. Exact preference values and claim history require structured recall.

Key point Semantic similarity improves discovery; it does not replace provenance or confirmation.

02 / Memory foundations · knowledge graph

Keep the relationships behind a memory.

The graph connects sources, entities and structured claims so the system can inspect where a value came from and how it changed.

01

Claims + provenance

Structured claims associate a subject with a field and value, backed by source records. Scope, authority and confirmation rules determine how claims are accepted and recalled.

02

Versions + time

Claim history preserves changes rather than treating every old statement as the latest value. Historical exact recall needs an explicit subject, field and relevant time.

03

How vectors complement it

Graph structure supports explicit relationships, while embeddings find related source text. Both use shared source identities in FalkorDB; the system does not maintain two unrelated memory copies.

Key point Web evidence is indexed as external source evidence; it does not become a confirmed traveler preference.

03 / TinyFish → durable memory

From a web page to reusable evidence.

The implemented persistence path starts with a completed destination research job using Search and Fetch.

01

Capture + check

Search returns candidate URLs and Fetch returns readable pages. An evidence quote must occur in the fetched page and have a valid public source URL. A snippet alone cannot satisfy this gate.

02

Save + index

SQL commits an evidence version with its owner, source URL, quote, timestamps and expiry. Graph indexing then adds source vectors and links to external entities, topics, cited pages and older observations.

03

Recall + refresh

Recall selects eligible evidence for the owner and excludes stale or conflicting candidates. Missing evidence can queue bounded background research. Changed high-impact evidence flags dependent plans for review.

Key point SQL evidence stays durable if graph indexing is pending. A quote match verifies provenance, not factual truth.

03 / TinyFish tools

Choose a tool for the research step.

The three tools have distinct contracts. Their availability should not be confused with every agent calling every tool.

01

Search · discover

Default research client for Atlas, Haven, Saffron and Roam. It submits public destination or topic queries and returns candidate sources. Traveler preferences are not included in the public query.

02

Fetch · read

Turns selected URLs into readable page content. Destination research uses it for evidence capture. Haven, Saffron and Roam use it conditionally for venue extraction when a reader is configured.

03

Agent · interact

Optional injectable client for asynchronous browser goals, with polling and timeout cancellation. It can replace the default research client; there is no automatic Search → Fetch → Agent escalation.

Key point Direct role results need an explicit bridge before entering the SQL evidence ledger.

04 / Product workflow

How a request becomes a revisable trip.

Example walkthrough: the traveler requests a short trip, then changes a preference or revisits saved research.

01

Understand + delegate

The consultant and orchestrator interpret the request and coordinate specialist roles. Relevant stored preferences and eligible external evidence become context for the task.

02

Research + plan

Research roles discover destination, stay, food and attraction information. Planning and budget roles consume shared evidence and structured estimates. Research output is not a reservation or a verified booking quote.

03

Save + revise

A trip can be saved, reloaded and duplicated. A changed preference can guide a revision. Changed external evidence can flag a plan for review; it does not silently rewrite or book the trip.

Key point The dashboard separates saved project replay from the explicit Follow live mode.

06 / Conclusions + next steps

A shared memory with a refreshable view of the world.

The architecture combines semantic discovery, structured recall and sourced web research. Evaluation measures these responsibilities separately.

01

Implemented

Shared vector + graph storage, nine coordinated roles, Search/Fetch destination research, versioned external evidence, freshness checks and editable trip workflows.

02

Measured

Controlled evidence reuse reduces repeated fixture HTTP requests. Local retrieval samples have mixed results. Product checks cover saved trips and dashboard behavior; they are not a live answer-quality benchmark.

03

Next validation

Evaluate larger samples and generated answers, test historical-time recall, measure hosted end-to-end latency, and validate the optional Agent path plus the role-to-ledger bridge.

Key point Keep measured results, architectural illustrations and optional integrations clearly distinguished.
