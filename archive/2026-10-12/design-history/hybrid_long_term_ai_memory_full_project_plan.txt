HYBRID LONG-TERM AI MEMORY ARCHITECTURE
Vector Memory + Temporal Knowledge Graph + Contrastive Retrieval + Graph-Based Reasoning

MASTER PROJECT DESCRIPTION

1. PROJECT OVERVIEW

The project is about building a long-term memory architecture for AI systems.

The central problem is that current LLM-based applications generally have limited memory. They can process the current conversation and retrieve information from a vector database, but this does not necessarily mean that they understand the relationships, history, contradictions, importance, or evolution of that information.

Most simple memory systems work approximately like:

User conversation
       ↓
Extract memory
       ↓
Generate embedding
       ↓
Store in Vector DB
       ↓
Query
       ↓
Top-K cosine similarity
       ↓
LLM

This works reasonably well for straightforward semantic retrieval.

However, long-term memory is more complicated.

A person's information changes over time.

Some information is more important than other information.

Some memories contradict older memories.

Some memories are not directly similar to the query but become highly relevant through their relationships with other memories.

Therefore, the proposed system combines:

Vector Memory
+
Knowledge Graph
+
Temporal Information
+
Contrastive Retrieval
+
Graph Traversal
+
Reranking
+
Memory Management

The objective is to create a memory system that doesn't merely ask:

"Which memories have the highest semantic similarity to this query?"

but instead asks:

"Which memories, relationships, historical states, and supporting or contradicting pieces of evidence are actually useful for answering this query?"


2. THE CORE PROBLEM

The fundamental problem is semantic similarity is not the same thing as contextual relevance.

Consider a user having these memories:

Memory 1:
"I am learning Java."

Memory 2:
"I use Java for DSA."

Memory 3:
"I use Python for machine learning."

Memory 4:
"I previously used C++ for DSA."

Memory 5:
"I stopped using C++ for my DSA preparation."

Now suppose the user asks:

"What language am I currently using for DSA?"

A simple vector search could retrieve:

Java
C++
Python
DSA
learning

because all of them may be semantically related.

But the actual answer requires understanding:

Java → DSA
C++ → DSA
C++ → historical
Java → current
Python → ML

Therefore, we need something more than similarity.


3. WHY VECTOR DATABASES ARE STILL IMPORTANT

This project is not replacing vector databases.

Vector retrieval remains extremely useful because it provides an efficient way of narrowing down a huge memory collection.

Suppose the system has:

1,000,000 memories

It would be inefficient to perform graph reasoning over everything.

Instead:

1,000,000 memories
        ↓
Vector search
        ↓
Top 100 candidates
        ↓
Graph reasoning
        ↓
Top 10 useful memories

So the vector database acts as the first-stage retrieval mechanism.

It gives us semantic locality.


4. WHY A KNOWLEDGE GRAPH IS REQUIRED

A Knowledge Graph represents information as:

Entities
+
Relationships
+
Attributes
+
Metadata

For example:

Vansh
  │
  ├── uses → Java
  │            │
  │            └── used_for → DSA
  │
  ├── uses → Python
  │            │
  │            └── used_for → Machine Learning
  │
  └── works_on → Memory Architecture

The vector database knows that two pieces of text are semantically similar.

The graph knows how things are connected.

This becomes particularly useful for:

- multi-hop retrieval
- entity relationships
- temporal relationships
- contradictions
- dependencies
- historical information
- contextual expansion

6. DUAL REPRESENTATION OF EVERY MEMORY

One of the most important ideas is that a memory can have two representations.

Representation 1 — Semantic

The memory is converted into an embedding:

Memory
 ↓
Embedding
 ↓
Vector DB

This allows semantic retrieval.

Representation 2 — Structural

The same memory is analyzed for:

entities
relationships
attributes
time
confidence
importance

and represented in the graph.

Therefore:

                    MEMORY
                       │
             ┌─────────┴─────────┐
             │                   │
             ▼                   ▼
        Vector form         Graph form
             │                   │
       semantic meaning     relationships

This dual representation is the foundation of the proposed architecture.


7. MEMORY INGESTION PIPELINE

When new information enters the system, it goes through an ingestion pipeline.

For example:

"I've started using Java instead of C++ for my DSA preparation."

The system processes it through several stages:

Raw Input
   ↓
Preprocessing
   ↓
Memory extraction
   ↓
Embedding generation
   ↓
Entity extraction
   ↓
Relationship extraction
   ↓
Temporal analysis
   ↓
Contradiction detection
   ↓
Vector storage
   ↓
Graph update

This means the system does not simply store the raw text.

It attempts to understand what the memory means.

A conceptual memory object could contain:

├── normalized_text
├── embedding

Example:

{

  "timestamp": "...",
  "valid_from": "...",
  "valid_until": null,
  "importance": 0.82,
  "confidence": 0.94,
  "type": "preference"

This allows the system to reason about the memory later.


9. ENTITY EXTRACTION

The system needs to identify entities from memories.

For example:

"I use Java for the Striver DSA sheet."

Potential entities:

The entities become nodes in the graph.

(Vansh)
   │
   └── uses → (Java)
                │

The system also needs relationships.

For example:

Vansh
   │
   ├── uses → Java
   ├── uses_for → DSA

Relationships can have types such as:

Each relationship can also have metadata.

The graph should ideally be a typed temporal knowledge graph, rather than simply a collection of nodes.

A relationship can look conceptually like:

Source
  ↓

For example:

Vansh
   │

                      │

confidence = 0.94

12. QUERY PROCESSING

When a user asks something, the query should also be processed.

For example:

"What am I currently using for DSA?"

The system can identify:

Entity:
DSA

Intent:
current preference / current usage

Temporal requirement:
current

Semantic representation:
query embedding

This is important because the query itself contains information about what kind of retrieval is needed.

"Currently" means older memories shouldn't automatically receive equal weight.


13. FIRST-STAGE VECTOR RETRIEVAL

The first retrieval stage uses semantic similarity.

Query
 ↓
Query embedding
 ↓
Vector DB
 ↓
Similarity calculation
 ↓
Candidate memories

Suppose we retrieve:

Top 100 memories

These are not necessarily the final answers.

They are simply the candidate pool.


14. POSITIVE RETRIEVAL

The most semantically similar memories are our positive candidates.

For example:

Query:
"What am I using for DSA?"

Positive candidates:

1. "I use Java for DSA."
2. "I'm doing the Striver DSA sheet in Java."
3. "Java is my current language for DSA."
4. "I'm practicing DSA."

These have high cosine similarity.

They form the main retrieval pool.


15. CONTRASTIVE / NEGATIVE RETRIEVAL

This was one of the more unusual parts of the proposed architecture.

Instead of retrieving only the highest similarity memories, we also retrieve a small number of lower-similarity or contrastive memories.

The purpose is not to say:

"Low similarity = useless."

Instead:

Low-similarity memories can provide contrast, alternative possibilities, historical information, or contradictory evidence.

For example:

High similarity:
"I use Java for DSA."

Lower similarity:
"I used C++ for DSA."

The second memory might actually be extremely important because it explains the historical state.


16. THE 1/10 CONTRASTIVE RETRIEVAL IDEA

The initial proposal was approximately:

Positive candidates = N

Contrastive candidates ≈ N / 10

For example:

100 positive candidates
10 contrastive candidates

Then:

100 positive
+
10 contrastive
=
110 candidate memories

The important thing is that 1/10 is a starting hypothesis, not a permanent rule.

During evaluation, compare:

1/5
1/10
1/20
1/50

and determine whether contrastive retrieval actually improves results.

That turns this idea into something experimentally testable.


17. WHY CONTRASTIVE MEMORIES COULD HELP

Consider:

M1:
"I use Java for DSA."

M2:
"I used C++ for DSA."

M3:
"I use Python for ML."

Query:

"What am I currently using for DSA?"

M1 is directly relevant.

M2 is less relevant semantically, but potentially important because it tells us:

There was a previous state involving C++.

M3 is semantically related to programming but structurally unrelated to DSA.

The graph can then distinguish:

Java → DSA → current

C++ → DSA → historical

Python → ML → unrelated to DSA

So contrastive retrieval provides candidate evidence, while graph reasoning determines its meaning.


18. CANDIDATE POOL CONSTRUCTION

After the first stage:

Positive candidates
        +
Contrastive candidates
        ↓
Candidate Pool

For example:

100 positive
10 contrastive

The system now has 110 potential memories.

But it still doesn't want to send all 110 to the LLM.

That's where the next stage comes in.


19. THE IRON WEB LAYER

This is the conceptual layer that connects semantic retrieval with graph reasoning.

The basic idea is:

Vector DB
   ↓
Top ~100 memories
   ↓
Iron Web Layer
   ↓
Graph relationships
   ↓
Expanded evidence
   ↓
Reranking
   ↓
Top ~10

The name "Iron Web" represents the idea of a strong structural web around the initial semantic candidates.

The vector DB finds the neighborhood.

The graph explores that neighborhood.


20. GRAPH EXPANSION

Suppose vector retrieval gives:

Memory A:
"I use Java for DSA."

The graph can expand from Java:

Java
 ├── used_for → DSA
 ├── used_by → Vansh
 ├── related_to → Striver
 └── previous_language → C++

Now the system has information that wasn't necessarily contained directly inside the retrieved text.

This is graph-based evidence expansion.


21. MULTI-HOP RETRIEVAL

Graph traversal can also find information indirectly connected to the query.

For example:

Vansh
 ↓
Project
 ↓
Technology
 ↓
Language
 ↓
DSA

A vector search may not retrieve every relevant memory.

Graph traversal can discover those relationships.

This becomes especially useful for questions such as:

"Which technologies am I using in the project that I'm currently working on?"

The answer may require multiple hops.


22. TEMPORAL MEMORY

Long-term memory must understand time.

Consider:

2025:
"I use C++ for DSA."

2026:
"I switched to Java for DSA."

Both statements are true within their respective time periods.

Therefore, deleting the old memory would actually lose useful historical information.

Instead:

C++ → DSA
valid_until = 2026

Java → DSA
valid_from = 2026

The system can then answer:

"What did I use previously?"

and:

"What do I use now?"

correctly.


23. CONTRADICTION DETECTION

Contradictions are expected in long-term memory.

Examples:

"I prefer X."

"I don't prefer X anymore."

or:

"I use C++ for DSA."

"I switched to Java for DSA."

The system should not blindly overwrite one with the other.

Instead, it can establish:

M1
 │
 └── CONTRADICTED_BY → M2

This allows the memory system to preserve historical knowledge while understanding which statement is currently valid.


24. SUPERSESSION

Some contradictions are actually state transitions.

For example:

C++ → old state
Java → new state

Rather than treating these as a permanent logical contradiction, the system can represent:

C++ memory
   │
   └── SUPERSEDED_BY → Java memory

This is much more appropriate for personal memory.

The older memory remains available for historical queries, while the newer memory receives higher relevance for current queries.


25. MEMORY IMPORTANCE

Not every memory deserves equal treatment.

For example:

"I ate pizza yesterday."

is probably less important long-term than:

"I am working on a research project about AI memory."

Therefore, memories can have an importance score.

Conceptually:

importance ∈ [0,1]

Higher importance can influence:

- retrieval
- decay
- storage
- context selection
- graph retention


26. MEMORY DECAY

Temporary information can become less important over time.

For example:

"Today's meeting is at 3 PM."

should eventually become less relevant.

But:

"User's permanent project architecture."

should decay much more slowly.

The important idea is:

If a memory has a value of 1, it should effectively behave as a hard truth and should not decay.

So conceptually:

importance = 1
       ↓
no decay

while lower-value memories decay according to time and usage.


27. RETRIEVAL FREQUENCY AND MEMORY STRENGTH

Decay should not necessarily depend only on time.

Suppose:

Memory A:
created 1 year ago
retrieved 100 times

Memory B:
created 1 month ago
never retrieved

Memory A may actually be more important.

Therefore, memory strength could depend on:

age
+
retrieval frequency
+
importance
+
confidence
+
user confirmation
+
relationship strength

This gives us a more realistic long-term memory model.


28. RERANKING

After vector retrieval and graph expansion, we have a large evidence set.

We now need to decide:

"Which memories should actually be passed to the LLM?"

A conceptual scoring function could be:

FinalScore =
      α × SemanticSimilarity
    + β × GraphRelevance
    + γ × Recency
    + δ × Importance
    + ε × EntityMatch
    + ζ × RelationshipStrength
    + η × HistoricalRelevance
    - θ × ContradictionPenalty

The exact weights should be experimentally determined.

This is another place where the research component becomes important.


29. CONTEXT COMPRESSION / SELECTION

Suppose the system has:

110 candidates

We don't want:

110 memories → LLM

Instead:

110 candidates
      ↓
graph reasoning
      ↓
reranking
      ↓
Top 10–20
      ↓
context assembly
      ↓
LLM

This reduces:

- token usage
- noise
- irrelevant context
- latency

while preserving the most useful evidence.


30. FINAL LLM REASONING

The LLM should ultimately receive structured evidence, not an uncontrolled dump of memory.

For example:

Relevant current memory:
"I use Java for DSA."

Historical memory:
"I previously used C++ for DSA."

Temporal relationship:
"C++ memory was superseded by Java memory."

Related entity:
"Striver DSA"

Then the LLM can reason:

"The user currently uses Java for DSA, while C++ was used previously."

The LLM is therefore doing reasoning over retrieved evidence, rather than trying to reconstruct the user's history from raw vector results.

32. MEMORY MAINTENANCE PIPELINE

Retrieval isn't the only thing the system needs.

A long-term memory system also needs periodic maintenance.

The maintenance system can perform:

duplicate detection
        ↓
stale-memory detection
        ↓
importance adjustment
        ↓
confidence adjustment
        ↓
contradiction detection
        ↓
relationship cleanup
        ↓
summarization
        ↓
memory consolidation

Maintenance can occur at different intervals such as:

daily
weekly
monthly

However, it should not blindly delete old memories.

Historical information can remain useful.


33. MEMORY CONSOLIDATION

If many memories describe essentially the same fact:

"I use Java."

"I'm learning Java."

"I'm using Java for DSA."

"Java is my DSA language."

the system can identify their common semantic core.

It can potentially consolidate them into:

"User uses Java for DSA."

while retaining references to the original memories.

This reduces redundancy.


34. DEDUPLICATION

Duplicate memories can waste storage and retrieval capacity.

For example:

M1:
"I use Java for DSA."

M2:
"Java is what I use for DSA."

M3:
"I'm doing DSA in Java."

These may represent essentially the same information.

The system can detect high semantic similarity and potentially combine them.

But source information should not necessarily be lost.

41. THE MAIN RESEARCH QUESTION

The project should not be presented merely as:

"I am building a better memory system."

A stronger research question is:

"Can a hybrid memory architecture combining semantic vector retrieval, contrastive candidate retrieval, temporal knowledge graphs, graph-based evidence expansion, and reranking improve long-term contextual retrieval compared with vector-only memory systems?"

That gives the project something measurable.


42. RESEARCH HYPOTHESIS

The hypothesis could be:

"A memory architecture that combines semantic similarity with structural relationships, temporal validity, and contrastive evidence will provide more accurate and contextually relevant memory retrieval than a vector-only retrieval architecture."

This can be tested experimentally.

M1

53. EXPECTED PROBLEMS AND CHALLENGES

There are also real challenges.

Graph extraction errors:
An LLM may extract an incorrect relationship.

Embedding errors:
Semantically similar memories may still be contextually different.

Graph growth:
Long-term memory could produce a very large graph.

Contradiction ambiguity:
Two statements may appear contradictory but actually refer to different contexts.

Temporal ambiguity:
Users don't always explicitly provide dates.

Retrieval latency:
Graph traversal plus vector search plus reranking adds computation.

Over-retrieval:
The graph can introduce irrelevant neighboring memories.

This is why evaluation is necessary.

57. ONE-MINUTE EXPLANATION FOR YOUR MENTOR

If your teacher asks:

"Okay, explain your project simply."

You can explain it like this:

"We are working on a long-term memory architecture for LLM-based agents. Most basic memory systems represent past information as embeddings and retrieve memories using cosine similarity. The problem is that semantic similarity doesn't always represent actual contextual relevance, especially when information changes over time, contradicts previous information, or is connected through relationships.

Our approach stores each memory in two parallel representations: a vector representation for semantic retrieval and a structured knowledge-graph representation for entities and relationships. When a query arrives, we first use vector search to retrieve a relatively large candidate set. Along with highly similar memories, we also retrieve a smaller set of lower-similarity or contrastive memories because those can contain historical or contradictory evidence.

These candidates then pass through what we're calling the Iron Web Layer. This layer uses the knowledge graph to expand relationships, perform graph traversal, identify temporal information, and find contradictions or superseded memories. A reranking mechanism then combines semantic similarity, graph relevance, temporal validity, importance, and other factors to select the most useful memories. Only the final evidence is passed to the LLM.

The research question is whether this hybrid semantic-plus-graph architecture can improve long-term memory retrieval compared with conventional vector-only memory systems. We would test this through baselines and ablation studies, including measuring the effect of the knowledge graph, contrastive retrieval, temporal information, and reranking independently."

FINAL PROJECT STATEMENT

The project proposes a hybrid long-term memory architecture for LLM-based agents. Instead of relying exclusively on vector similarity, the system maintains a dual representation of memories using both semantic embeddings and a temporal knowledge graph. During retrieval, a query is first used to obtain a broad semantic candidate set from the vector database. A smaller contrastive candidate set is also retrieved to preserve potentially useful historical, alternative, or contradictory evidence. These candidates are passed through an Iron Web Layer, which performs knowledge-graph traversal and evidence expansion while considering entities, relationships, temporal validity, contradictions, and memory importance. A memory-aware reranker then selects the most relevant evidence for the final context supplied to the LLM.

The proposed architecture will be evaluated against progressively more capable baselines, including vector-only retrieval, vector plus reranking, vector plus graph retrieval, and vector plus contrastive retrieval. Ablation experiments will independently remove graph reasoning, contrastive retrieval, temporal information, and other components to determine their individual contribution. The contrastive retrieval ratio, initially hypothesized at approximately one contrastive memory for every ten positive memories, will also be experimentally varied rather than treated as a fixed assumption.

The ultimate objective is to determine whether combining semantic similarity, structural relationships, temporal state, contrastive evidence, and memory-aware ranking can improve the accuracy, relevance, robustness, and efficiency of long-term memory retrieval for LLM agents.
